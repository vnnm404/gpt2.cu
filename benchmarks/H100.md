# H100 training measurements

Measured on one NVIDIA H100 80GB HBM3 (132 SMs), PyTorch 2.5.1+cu124,
CUDA 12.4, GPT-2 124M, sequence length 128. These are **physical batches**,
without gradient accumulation. The reference is eager PyTorch FP32, TF32 disabled,
with fused AdamW. The custom step is one cooperative persistent kernel.

| Batch | Tokens/step | PyTorch GPU ms | Hopper GPU ms | Speedup | Hopper tokens/s (wall) |
|---:|---:|---:|---:|---:|---:|
| 32 | 4,096 | 91.118 | 81.385 | 1.120× | 50,265 |
| 64 | 8,192 | 171.713 | 157.712 | 1.089× | 51,910 |
| 128 | 16,384 | 327.044 | 324.260 | 1.009× | 50,511 |

Each result is a median of 50 timed steps after five warmup steps. Five checked
training steps precede timing. Batch 128 is effectively parity: a sub-1% margin
in a single measurement is not a robust throughput advantage. The before-change
SIMT executor took 120.651 ms at batch 32 and 226.258 ms at batch 64.
Raw results, source hashes, and all checked losses are in [h100/](h100/).

## Arithmetic and validation

State, activations, gradients, parameters, and Adam moments remain FP32. GEMMs
pack operands into high/middle/low BF16 components and retain six products:
HH, HM, MH, MM, HL, and LH. WGMMA accumulates HH and the corrections separately
in FP32, then combines them. This approximates FP32; it is neither bitwise FP32
nor ordinary BF16 training. Packing and split-K reduction costs are included.
No result here establishes performance against AMP, torch.compile, CUDA Graphs,
longer contexts, or different models.

The original checks were retained: loss atol/rtol 2e-5; logits 3e-4;
all gradients atol 3e-5, rtol 3e-3 plus relative RMS below 2e-3 (or absolute error
below 2e-7); all updated parameters atol 1e-4, rtol 3e-4. They pass for five steps
at every reported batch. These finite checks do not establish equivalent
long-run convergence.

Batch 128 uses `--isolated`: run the two engines in separate processes, save
reference weights, gradients, logits, and losses, and validate the CUDA engine
against those snapshots. Both still use batch 128. Keeping both engines alive
together exceeds device memory. Snapshot I/O is outside timing; allow about
20 GB temporary disk space for five checkpoints.

## Hopper implementation and scheduling

`hopper_gemm.cuh` contains the inline packing and GEMM implementation. Packing
uses vector global reads/writes and a bank-conflict-free shared transpose. Two
scratch arenas are reused, with byte-range dependency tracking preventing early
overwrite. GEMM tiles are 64×128×32 with two warp groups and three TMA pipeline
stages. Each stage carries six packed operand tiles. Shared memory is 112 KiB
per CTA, allowing two resident CTAs per SM on this device. Split-K bounds long
reductions and supplies work to the resident grid; partition selection rejects
empty tails. Logical row grouping improves weight reuse across workers.

TMA transfers complete through transaction `mbarrier` waits. WGMMA completion
and a CTA barrier precede stage reuse; all transactions drain before barrier
invalidation. Packing's generic global stores execute `fence.proxy.async.global`
before the cooperative grid barrier exposes them to TMA consumers. Hardware
transaction barriers protect local pipelines; global producer/consumer edges
still use cooperative grid barriers. See NVIDIA's [Hopper tuning guide](https://docs.nvidia.com/cuda/hopper-tuning-guide/)
and [PTX proxy and asynchronous-operation semantics](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html).

Worker count is actual SM count times compiled-kernel occupancy, queried after
shared-memory opt-in. Oversized cooperative grids are rejected. Idle workers
participate in every grid barrier. No physical SM affinity is assumed. All
device implementations remain visible in one translation unit, without device
linking boundaries. Unpacked FP32 descriptors and unsupported packing shapes
retain the SIMT path. Cross-entropy uses Hopper's fast exponential intrinsic;
there is no global `--use_fast_math` compiler flag.

## Reproduce

```sh
python benchmarks/check_runtime.py
python benchmarks/check_hopper.py
python benchmarks/gemm.py --tokens 8192
for batch in 32 64; do
  python benchmarks/compare.py --batch "$batch" --sequence 128 \
    --steps 5 --iterations 50 --output "h100-b${batch}.json"
done
python benchmarks/compare.py --isolated --batch 128 --sequence 128 \
  --steps 5 --iterations 50 --output h100-b128.json
for tool in synccheck memcheck racecheck; do
  timeout 300 compute-sanitizer --tool "$tool" --error-exitcode 99 python benchmarks/check_hopper.py
done
```

The Python loader selects `sm_90a` and pinned CUTLASS 3.5.1 automatically on H100.
For CMake, use `-DCMAKE_CUDA_ARCHITECTURES=90a`. See [BUILD.md](../BUILD.md).
The runtime checks cover dependency chains, residency rejection, odd split-K
sizes, Adam parameters/moments, and all operations at sequence lengths
1, 17, 64, and 256. Hopper checks exercise transposes, tile tails, pipeline phase
reuse, bias/add, raw FP32 fallback, and repeated launches at 1, 3, and 264 workers.

## Matched mini training run

Three fresh-process runs per engine, 200 steps each, batch 64 × sequence 128
(1,638,400 tokens). The corpus is [Tiny Shakespeare](https://raw.githubusercontent.com/karpathy/char-rnn/master/data/tinyshakespeare/input.txt),
encoded with the GPT-2 tokenizer. Each engine starts from the same random seed
123 and identical contiguous next-token batches. The previous SIMT executor is
commit `1d5cc26`, using the same training harness.

| Engine | Median total wall seconds | Three runs (seconds) | Final loss |
|---|---:|---|---:|
| PyTorch eager FP32 | 34.061 | 34.061, 33.978, 34.063 | 5.304100 |
| Previous SIMT megakernel | 45.248 | 44.948, 45.248, 45.252 | 5.304109 |
| Hopper megakernel | 31.581 | 31.581, 31.581, 31.591 | 5.304104 |

Hopper saves **2.479 seconds (7.3%)** against PyTorch and **13.667 seconds (30.2%)**
against the previous megakernel. Maximum absolute per-step loss difference
against PyTorch across all three Hopper runs is **1.574e-5**. Timed work includes
batch copies, forward, backward, AdamW, and recording losses. Dataset loading,
tokenization, compilation, construction, and five reset warmup steps are excluded.
All 200 losses and timing/memory metadata are retained in `h100/train-*.json`;
`h100/training-summary.json` records the aggregate.

```sh
curl -L https://raw.githubusercontent.com/karpathy/char-rnn/master/data/tinyshakespeare/input.txt -o /tmp/shakespeare.txt
for mode in pytorch persistent; do
  python benchmarks/train.py --text /tmp/shakespeare.txt --batch 64 --sequence 128 \
    --steps 200 --mode "$mode" --output "train-$mode.json"
done
```

The mini-run requires `tiktoken`. Repeat three times with distinct output paths.

## Final checks and compute cost

Final `synccheck` and `memcheck` report zero errors; `racecheck` reports zero
hazards, errors, or warnings. Both `sm_90a` and `sm_86` CMake builds pass. Runtime
checks and Python syntax checks pass. Logs are retained in `h100/`.

Standalone GEMM measurements include packing and split-K reduction:

| M × N × K | Separate operations ms | Persistent ms | PyTorch mm ms |
|---|---:|---:|---:|
| 8192 × 2304 × 768 | 0.367 | 0.394 | 0.665 |
| 8192 × 768 × 3072 | 0.665 | 0.689 | 0.872 |
| 3072 × 768 × 8192 | 0.635 | 0.655 | 0.798 |
| 8192 × 50304 × 768 | 6.926 | 7.574 | 12.248 |
| 8192 × 768 × 50304 | 10.641 | 13.319 | 13.018 |
| 50304 × 768 × 8192 | 9.477 | 11.589 | 11.900 |

The long vocabulary reduction remains slightly slower in the persistent
schedule, despite its faster separate-operation implementation. The full-step
measurements include this cost.

The H100 rental was destroyed and its absence verified after collecting results.
Elapsed rental time was about 64 minutes at $1.744444/hour including disk:
**approximately $1.86**, below the **$10 compute cap**. This is a rate-based
estimate, not an invoice. Exact timestamps and calculation are in `h100/cost.json`.
A four-hour automatic destruction guard was installed during experimentation.
